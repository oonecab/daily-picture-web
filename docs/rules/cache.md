# 缓存、重试与失败规则

状态：CURRENT；基线版本：1.5.0；生效日期：2026-10-21；维护角色：项目维护者。

权威范围：服务侧 [lib/bing.mjs](../../lib/bing.mjs)；浏览器侧补充见 [浏览器状态](browser-state.md)。以下是当前设计与实现，不是上游 SLA 或经过压力测试的容量承诺。

## DP-METADATA：归档提交独立于图片

每个市场独立保存 schemaVersion=1、windowDays=15 的归档。两批均成功规范化并合并后，先写临时文件再重命名提交到 `.cache/archives/<market>.json`，然后替换进程内缓存。任一批获取/解析/验证失败时保留上次完整归档，不提交另一批的部分结果。即使图片 ID 全未变化，标题、版权、顺序等元数据仍提交；不能以“未下载新图片”为由跳过。

缺失或不能通过现有 schema/市场/日期时间/图片 ID 检查的磁盘缓存不阻断网络恢复。这不是对缓存所有字段的完整 schema 校验。提交失败不会报告 fresh，而是进入错误处理和已有缓存回退。

## DP-CACHE：命中与旧数据

归档在线 TTL 为 15 分钟，只有 `windowDays=15` 的当前窗口可直接命中。旧七张缓存保持可读，但缺少此标识时即使仍在 TTL 内也重新获取；失败时保留旧缓存并明确 stale 回退。手动 `refresh=1` 跳过 TTL，但仍受下述刷新冷却限制；同市场在途请求共享一组两批请求的 Promise。缓存状态：

| cache | stale | 含义 |
| --- | --- | --- |
| `hit` | false | 尚在本地 TTL 内，未必此次访问过网络 |
| `fresh` | false | 此次上游归档已规范化并提交 |
| `cooldown` | 保留上次结果 | 距本市场上次刷新启动不足 30 秒，复用上次结果；`retryAfter` 为剩余整秒数，向上取整 |
| `fallback` | true | 获取/提交失败，使用服务上次可用归档 |
| `browser-offline` | true | Service Worker 网络失败或错误响应后从浏览器回退；不必然等同设备完全断网 |

每个服务进程按市场记录实际刷新启动时间；30 秒内复用结果或重抛上次无缓存错误，不再次请求 Bing。失败回退的 `stale` 和警告在冷却期保留；普通请求仍可命中 15 分钟 TTL。冷却是内存状态，重启后重新建立。前端手动刷新命中冷却时提示稍后重试，不宣称本次已访问上游。

没有可回退归档时上游失败返回 502，资源队列满返回 503；Service Worker 无归档可回退时为 503。前端保留已有视图并展示错误或旧数据标识。不能把缓存状态隐藏成“最新同步”。

图片键为 `<id>_<size>.jpg`，同键网络请求合并。磁盘命中会检查 JPEG 起始字节；新网络响应要求 `image/jpeg` 类型及起始字节。这不等价于完整解码验证。

每日精选与历史按需图片共享一个 image-cache 实例及目录，最多 140 项、256 MiB。启动时清理本模块遗留临时写入并恢复预算；所有写入串行化，在创建临时文件前按修改时间淘汰旧项并预留新文件空间，原子重命名完成提交。超出单图/总预算的文件不入缓存，失败响应不入缓存；缓存写入失败不妨碍返回已验证的上游图片。受保护副本和永久缩略图不属于临时缓存。反向代理关闭额外图片缓存和临时落盘。浏览器预算与配额恢复以 [DP-LOCAL](browser-state.md) 为准。长期压力和浏览器主动驱逐尚未实测。

## DP-RESOURCE：上游总量限制

同一服务实例的图片、两批归档及历史月度/图片请求共用最多 4 个上游执行槽、32 个等待位置；同键请求合并后占用一个操作。槽位覆盖 fetch、读体和重试退避，成功或失败均释放。队列满立即返回 503（有旧归档时仍可 stale 回退），HTTP 层提供 `Retry-After: 5`；排队不额外延长原有 20 秒预算，超时移除等待项。

默认值为本地隔离负载验证后的保守资源预算，不是公网吞吐承诺。测试可通过 `createBingService` 的 `maxConcurrent`、`maxQueued`、`requestTimeoutMs`、`refreshCooldownMs` 注入更小边界；它们不新增环境变量。生产反向代理限流需结合实例流量独立配置。应用的限制针对上游操作，不等价于所有 HTTP/磁盘读取的连接限制。

1.4.2 另外增加跨每日精选/历史图片的 HTTP 共享缓冲区池，并对历史媒体读盘单独设限；保留预算直至响应完成/关闭，等待和慢连接均有时限。该边界由 [DP-HISTORY-IMAGE](history.md#dp-history-image图片可用性与资源预算) 统一定义，与这里的上游执行槽独立。

## DP-RETRY：失败预算

每批归档或单张图片最多两次 fetch：连接失败或首次 HTTP 408/429/5xx 时等待 300ms 后再试一次。两批归档并行提交到资源队列，与排队、重试和读体共用一个 20 秒 AbortSignal，合计通常 2 次、最多 4 次 fetch；等待两批都结束后再提交或回退。单张图片及其重试另用一个 20 秒信号。退避等待可被该信号取消。其他 HTTP 错误直接失败；读取响应体、JSON 解析或图片验证失败不由该循环重新尝试。不得描述为无限重试或两个串行的 20 秒预算；信号时限也不是毫秒级完成时刻保证。

每批归档读取上限 1 MiB，图片 20 MiB，检查 Content-Length 并累计实际流量；禁止重定向。失败记录错误上下文及可用底层原因。曾出现的 `fetch failed` 根因仍未确定，见 [开放问题](../../issues/002-upstream-connection.md)；有重试不意味着已修复网络根因。
