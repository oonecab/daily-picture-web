# 缓存与资源可靠性验收

状态：本地验收通过，待 Git 交付；日期：2026-10-20（Asia/Shanghai）。关联：[问题 012](../../issues/012-cache-resource-reliability.md)、[计划 008](../../plans/008-cache-resource-reliability.md)。

## 测试设计

- SW-01：缓存外壳在断网、5xx、超时后回退；4xx 保持原错误；恢复联网更新缓存；响应头和正文阶段的超时均覆盖。
- SW-02：图片配额异常清理后只重试一次，失败通知页面；条数与字节预算；并行写入不突破清理目标；旧收藏与数据缓存升级保留。
- RES-01：不同图片与两批归档共享总并发预算；同键仍合并；队列满返回可重试 503；排队、重试、读体共享时限，失败后释放槽位；地区独立冷却；失败结果不能被冷却伪装为 fresh。
- UI-01：切图保持缩略图节点和焦点；选中属性、收藏标记与列表切换正确；实际桌面/窄屏用键盘操作；冷却与离线存储失败提示准确。
- HTTP-01：相同资源条件请求为 304，不匹配标识为 200；HEAD、弱比较、多标签、通配与 API 原策略。
- 执行 `npm run check`、`npm test`、`python3 -X utf8 tools/verify_research.py`、差异与文档一致性检查。

## 结果

环境为本地 macOS、Node.js 24.21.0、Python 3.14.6 与 Ego Chromium。测试使用合成归档和图片，不对 Bing 或生产站点施压。

### 自动回归与失败证明

在基线 `9ee56da` 上添加第一批测试后，42 项中 13 项失败，覆盖缩略图节点/焦点、总并发、排队超时、冷却、ETag、5xx/超时回退和配额/预算。原有 27 项全部通过。修复后的复核又发现“头部已到而正文超时”被缓存写入 catch 吞掉的问题；新增单项测试先失败，再加入 AbortSignal 检查并通过。原有元数据更新及部分归档失败测试仅将注入时钟推进 30 秒以触发冷却后的实际刷新，原完整性断言保留。

最终 `npm run check` 退出 0；`npm test` **48/48 通过，0 失败、0 取消、0 跳过**（16 项原服务回归、14 项 UI、8 项资源/HTTP、10 项 Service Worker）。`python3 -X utf8 tools/verify_research.py` 检查 238 个文件、432 个本地引用，失败列表为空；未与外部原目录逐字比较。`git diff --check` 通过。规则字面引用及命令事实检查通过；这类检查不替代上述行为验证。

### 真实浏览器与隔离负载

- 真实 Service Worker 从 1.1.0 升到 1.1.1：旧外壳删除，200 条合成收藏、偏好 JSON、地区归档和预存图片保留。
- 桌面浏览列表按回车切图，原 15 个缩略图全部保留，焦点仍在按钮。实测 393×852 窄屏下，200 个收藏节点全部保留，选中属性、焦点和横向滚动保持，页面无横向溢出；截图检查通过。
- 源站直接读取为 HTTP 503 时，浏览器导航仍返回缓存页面（200），应用与 200 条收藏可用。源站延迟 6.5 秒时，约 5.19 秒显示缓存应用；恢复源站后重新加载正常。
- 24 个不同图片请求，各响应 1 MiB、假上游读体延迟 20ms。执行槽为 24/8/4 时，峰值读体并发分别为 24/8/4，总耗时约 46/70/132ms。选择 4 作为保守默认；排队降低同时读体数量，也增加批量完成时间。这不是公网延迟或进程 RSS 测量。队列拒绝、共享归档池与超时释放另由可执行回归覆盖。
- ETag 的强/弱、多值、通配 GET 返回 304 且无响应体；过期标识返回 200；HEAD 和 API 原缓存策略通过回归。

本机完整日志、JSON 与截图位于 Git 忽略的 `test-output/reliability-fix-20261020/`。测试源码随仓库提交；临时夹具服务在验收后关闭。

### 边界

QuotaExceededError 为可重复故障注入，未耗尽真实设备磁盘；读体超时含 VM 流式故障注入。真实手机触摸、其他浏览器、长期运行、生产 Nginx 限流与真实用户分位数仍需独立验收。本次未改生产环境、环境变量、监听地址或持久化 schema，也不将历史真实 Bing 实测更新为本次结果。
