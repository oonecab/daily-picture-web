# 发布与回滚

本文提供通用发布与回滚流程，配置要求见 [环境事实](environments.md)，公开访问入口见 [README](../README.md)。部署需要明确授权和相应管理权限。

执行前从私有运维记录确认应用根目录、状态目录、服务单元、运行账户及当前版本目标。下文的 `releases/`、`current` 和 `<release>` 表示版本布局示例，由部署者映射到实际配置；管理地址、账户、绝对路径和配置快照保存在私有位置。

## 发布过程

1. 核对分支、远端与待交付差异；运行 package.json 中 check/test、研究完整性检查，并审查暂存文件和敏感内容。提交后普通推送，核对远端 SHA。
2. 从已推送提交用 `git archive` 提取 `server.mjs`、`lib/`、`public/`、`package.json`、`test/`、`LICENSE`、`THIRD_PARTY_NOTICES.md`。生成 SHA-256 清单与包含提交 SHA 的发布元数据，不打包开发缓存或本地配置。
3. 上传到新的 `releases/<release>`。核对运行文件摘要，在该目录用已确认的 Node 执行语法检查和测试；把 `.cache` 链接到持久化状态目录；1.2.0 还须设置独立、可写且跨版本稳定的 `HISTORY_DIR`（或 `.history` 链接），并备份月索引。代码由部署管理者维护、服务账户可读，状态目录由服务账户写入。
4. 在私有运维记录中保存旧 current 目标和服务/反向代理配置摘要。先创建临时链接，再以同目录原子重命名替换 current；重启已确认的应用服务。
5. 检查服务 active、回环健康、HTTPS、运行文件摘要和真实页面。客户端已有页面需重新加载以取得新的静态资源。确认收藏存储键、缓存位置、来源及版权展示仍符合规则。
6. 公开验收记录保存日期、提交 SHA、文件摘要、验证结果及限制，实例操作明细保留在私有运维记录。检查公开文件及附件后推送并读取远端；如只有验收文档追加提交，须证明最终 HEAD 的运行文件与已发布版本逐一相同。

## 回滚

激活后若服务无法启动、健康检查失败或关键页面异常，立即用保留的旧目标重新创建临时链接并原子替换 current，再重启服务。以健康响应、旧版运行文件摘要及实际页面确认恢复。旧版本目录、状态目录和配置备份在新版本验收完成前保留。

[1.1.1 发布验收](testing/reliability-release.md) 与 [历史发布验收](testing/mobile-release.md) 保存公开可核对的提交、摘要与验证结果。实际目录、回滚目标和配置备份从私有运维记录读取；长期安装配置遵循已确认的环境要求。

1.2.0 回滚时保留历史目录，不用旧版本删除该目录；旧版本会忽略新增历史索引。更新/回滚均需确认 Service Worker 升级、原收藏保留及历史收藏的兼容边界（1.1.x 不识别新增历史图片路由）。
