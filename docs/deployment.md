# 发布与回滚

本文提供通用发布与回滚流程，配置要求见 [环境事实](environments.md)，公开访问入口见 [README](../README.md)。部署需要明确授权和相应管理权限。

执行前从私有运维记录确认应用根目录、状态目录、服务单元、运行账户及当前版本目标。下文的 `releases/`、`current` 和 `<release>` 表示版本布局示例，由部署者映射到实际配置；管理地址、账户、绝对路径和配置快照保存在私有位置。

## 发布过程

1. 核对分支、远端与待交付差异；运行 package.json 中 check/test、研究完整性检查，并审查暂存文件和敏感内容。提交后普通推送，核对远端 SHA。
2. 从已推送提交用 `git archive` 提取 `server.mjs`、`lib/`、`public/`、`package.json`、`package-lock.json`、`tools/`、`test/`、`LICENSE`、`THIRD_PARTY_NOTICES.md`。生成 SHA-256 清单与包含提交 SHA 的发布元数据，不打包开发缓存或本地配置。
3. 上传到新的 `releases/<release>`。核对运行文件摘要，在目标平台执行 npm ci 安装 Sharp；用已确认的 Node 执行语法检查和测试；把 `.cache` 链接到持久化状态目录；1.2.0 还须设置独立、可写且跨版本稳定的 `HISTORY_DIR`（或 `.history` 链接），并备份月索引。代码由部署管理者维护、服务账户可读，状态目录由服务账户写入。
4. 在私有运维记录中保存旧 current 目标和服务/反向代理配置摘要。先创建临时链接，再以同目录原子重命名替换 current；重启已确认的应用服务。
5. 检查服务 active、回环健康、HTTPS、运行文件摘要和真实页面。客户端已有页面需重新加载以取得新的静态资源。确认收藏存储键、缓存位置、来源及版权展示仍符合规则。
6. 公开验收记录保存日期、提交 SHA、文件摘要、验证结果及限制，实例操作明细保留在私有运维记录。检查公开文件及附件后推送并读取远端；如只有验收文档追加提交，须证明最终 HEAD 的运行文件与已发布版本逐一相同。

## 回滚

激活后若服务无法启动、健康检查失败或关键页面异常，立即用保留的旧目标重新创建临时链接并原子替换 current，再重启服务。以健康响应、旧版运行文件摘要及实际页面确认恢复。旧版本目录、状态目录和配置备份在新版本验收完成前保留。

[1.1.1 发布验收](testing/reliability-release.md) 与 [历史发布验收](testing/mobile-release.md) 保存公开可核对的提交、摘要与验证结果。实际目录、回滚目标和配置备份从私有运维记录读取；长期安装配置遵循已确认的环境要求。

1.2.0 回滚时保留历史目录，不用旧版本删除该目录；旧版本会忽略新增历史索引。更新/回滚均需确认 Service Worker 升级、原收藏保留及历史收藏的兼容边界（1.1.x 不识别新增历史图片路由）。

[1.2.0 历史壁纸发布验收](testing/history-release.md) 记录独立历史目录、自动采集、原图下载及重启保留证据。

## 1.4.0 图库迁移

初次历史导入在独立目录执行，检查 import-report.json 的失败、隔离记录及媒体清单。图像文件不进入源码 Git；经检查的月索引可备份到本站 codex/wallpaper-data 分支，并保留第三方来源说明。发布前完成图片尺寸、完整解码、SHA-256 和离线读取验证。

停止旧服务后，再合并旧 HISTORY_DIR 的最新月记录到新图库，保留同日来源优先级、原记录与来源；复制同 ID 已保存图片时核对清单。保存迁移前后的日期/ID 集合及差异原因，不能因切换丢掉新采集日期。新版本的 .history 链接指向新图库，旧版本及旧图库保留；回滚只切回旧版本入口，两个图库均不删除。应用启动后核对 Actions 已写入最新索引、后台同步状态及媒体保存结果，并验证公网的缩略图、预览和原图下载。

GitHub Actions 使用固定提交的官方 checkout/setup-node，默认仅 contents:write；数据分支写入串行化、普通推送，不强制覆盖。调度可能延迟，验证一次成功执行不等于未来每日调度保证。

## 1.5.0 分层图库迁移

先逐条检查所有已索引历史图片的 Bing 原图和预览：保留实际变体、检查时间、HTTP/JPEG/完整解码结果、尺寸及摘要，优先 UHD，旧变体只能用于同一个 ID。失效、无法确认或低于已保存原图尺寸的图片均保留本站副本。报告是私有运行数据。

将完整图库备份到部署者本机。可利用 SHA-256 完全相同的 Bing 字节补齐本地备份；只接受与线上媒体清单逐字节一致的文件，剩余文件从服务器复制。用下列工具独立遍历全部媒体验证，不以传输成功代替校验：

```sh
node tools/migrate-history.mjs --backup-dir /path/to/local-backup --receipt /path/to/backup-receipt.json
```

发布新版本前保存旧代码及反向代理配置。检查 CSP 允许固定 Bing 图片来源；Nginx 图片代理使用 proxy_buffering off、proxy_max_temp_file_size 0、proxy_cache off。环境变量、监听和服务账户保持原配置。

停止服务写入，提供完整链接报告和备份校验凭据，先迁移索引而不清理文件：

```sh
node tools/migrate-history.mjs --offline --history-dir /path/to/history --audit /path/to/audit.json --receipt /path/to/backup-receipt.json
```

激活新代码并验证桌面/移动浏览、直接下载、本站回退、缩略图和后台同步。通过后再次暂停写入，以同样参数追加 --prune，工具完成整批预检后只删除满足检查与备份条件的 original/preview 文件；保留缩略图、索引和受保护副本。恢复服务，重新核对保留清单、磁盘空间和关键请求。无法确认的条目宁可保留，禁止通配符清理。

迁移可重复执行，已清理文件不会重复计入释放量。回滚至 1.4.x 全量图库版本前，必须从本机校验过的备份恢复原图/预览和迁移前索引，并核对摘要；仅回退代码不足以恢复旧存储行为。恢复需要传输时间，备份应保持可访问。新采集日期必须单独保留，不能用旧备份整目录覆盖。

## 1.6.0 海外历史扩展

本节为新增地区操作，不重跑中国全量导入或清理。代码版本、备份和具体实例路径由部署者管理；目录示例需替换为自己的绝对路径。

1. 在独立候选版本目录安装目标系统依赖，运行 `npm ci`、`npm run check`、`npm test`。保留当前版本入口和回滚目标。确认根分区可用空间高于 10 GiB，并为代码、索引与缩略图留出增长余量。
2. 用独立暂存根启动轻量导入：`node tools/import-regions.mjs --history-dir /path/to/staging-overseas --market all --concurrency 2`。最高允许 4 并发，不自动启用更大并发。每区产物在 `markets/<market>/`；只有月索引、缩略图、清单与导入报告，不应有 `.original.jpg` 或 `.preview.jpg`。
3. 检查所有地区 `import-report.json` 的完成时间、月份、条数、failures。瞬时失败可重跑相同命令；已保存缩略图核验后复用。异常退出时先确认原进程结束再移除唯一导入锁。不要将源端缺失日期补成其他图；缺失月份或无法解码的文件须单列，不能宣称完整成功。
4. 按月索引逐张核对媒体清单、字节数、SHA-256 和实际 JPEG 尺寸，确保记录 market、日期和 ID 与目录对应。保存导入前的中国月索引及保护副本摘要/备份。停止应用写入，把已验证的五个新增地区目录接入正式 HISTORY_DIR/markets；目标若已有同名地区目录，先备份并制定合并方案，不直接覆盖。中国 HISTORY_DIR 根文件和 media 不移动。
5. 推送 main 中的六区采集工作流；确认自己的数据分支包含原 latest.json 和五份 markets/<market>/latest.json。某区失败时其他成功地区仍提交，但工作流会报告失败。第三方源站故障不应通过改成任意图片代理解决。
6. 原子切换到候选代码，重启应用，检查健康接口 1.6.0、六区目录/首月/最新月、老美国图片的本站下载、最新图片、受保护中国图片以及各区 sync 状态。检查 nginx 不额外缓存或落盘图片，复核磁盘占用和浏览器实际页面。
7. 上线失败时切回原代码并重启；中国数据兼容旧版，新地区目录可独立保留。不要以恢复代码为由删除新数据或清空缓存/收藏。临时验证进程结束后可收尾本次暂存代码和私有日志，遵循部署者的保留策略。

备份包括中国和所有地区的索引、缩略图与保护副本。256 MiB 只限制共享临时图片缓存，不包含持久缩略图、备份或发布版本目录。按需图片仍依赖上游和服务器出站网络；大陆访问测试只能证明受测网络/时间可用，不能保证所有运营商永久可用。
