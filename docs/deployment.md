# 发布与回滚

生产入口为 [Daily Picture](https://dailypicture.zzzping.top/)。运行拓扑、用户、路径和端口以 [环境事实](environments.md) 为准。部署需要明确授权和现有 SSH 管理权限，登录材料不放入仓库。

## 发布过程

1. 核对分支、远端与待交付差异；运行 package.json 中 check/test、研究完整性检查，并审查暂存文件和敏感内容。提交后普通推送，核对远端 SHA。
2. 从已推送提交用 `git archive` 提取 `server.mjs`、`lib/`、`public/`、`package.json`、`test/`、`LICENSE`、`THIRD_PARTY_NOTICES.md`。生成 SHA-256 清单与包含提交 SHA 的发布元数据，不打包开发缓存或本地配置。
3. 上传到新的 `releases/<日期时间>-<提交短 SHA>`。核对运行文件摘要，在该目录用既有 Node 执行语法检查和测试；把 `.cache` 链接到既有状态目录。代码保持 root 管理、服务用户可读，状态目录由服务用户写入。
4. 保存旧 current 目标和服务/Nginx 配置摘要。先创建临时链接，再以同目录原子重命名替换 current；重启 `daily-picture.service`。
5. 检查服务 active、回环健康、HTTPS、运行文件摘要和真实页面。客户端已有页面需重新加载以取得新的静态资源。确认收藏存储键、缓存位置、来源及版权展示仍符合规则。
6. 写回发布验收记录，推送后读取远端；如只有验收文档追加提交，须证明最终 HEAD 的运行文件与已发布版本逐一相同。

## 回滚

激活后若服务无法启动、健康检查失败或关键页面异常，立即用保留的旧目标重新创建临时链接并原子替换 current，再重启服务。以健康响应、旧版运行文件摘要及实际页面确认恢复。旧版本目录、状态目录和配置备份在新版本验收完成前保留。

本轮 [发布验收](testing/mobile-release.md) 保存实际提交、目录、回滚目标与结果；长期安装配置遵循现有环境，不通过发布临时变更安全策略。
